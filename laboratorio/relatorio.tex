\section{Introdução}

A construção de sistemas distribuídos demanda mecanismos de comunicação interoperáveis, eficientes e de baixa latência, permitindo que componentes construídos em linguagens e plataformas distintas colaborem de forma consistente. Abordagens legadas, como chamadas HTTP/REST baseadas em serialização JSON ou troca direta de fluxos de bytes via sockets TCP brutos, introduzem custos adicionais de parsing em formato texto, ausência de validação rígida de tipos em tempo de compilação ou alto acoplamento manual entre as extremidades.

Para contornar tais desafios, o framework de comunicação remota \textbf{gRPC} (\textit{gRPC Remote Procedure Calls}), desenvolvido pela Google sobre o protocolo de transporte HTTP/2, consolida-se como um padrão moderno na indústria. O núcleo do gRPC é fundamentado na utilização de \textbf{Protocol Buffers (Protobuf)} como Linguagem de Definição de Interface (IDL - \textit{Interface Definition Language}) e mecanismo de serialização binária altamente compactada.

Neste projeto acadêmico, exploramos a integração entre:
\begin{enumerate}
    \item Um \textbf{cliente desktop em JavaFX}, que fornece a interface gráfica do usuário;
    \item Um \textbf{servidor remoto em Python}, encarregado de processar requisições e consultar as entidades cadastradas;
    \item Um \textbf{contrato estrito em Protocol Buffers (\texttt{laboratorio.proto})}, que atua como a única fonte da verdade (\textit{single source of truth}) compartilhada entre ambos os nós.
\end{enumerate}

O foco primordial deste trabalho está na especificação do arquivo de contrato \texttt{.proto}, no processo de geração dos stubs em ambas as linguagens, na implementação do serviço RPC em Python e na sua invocação assíncrona e resiliente na interface gráfica do cliente JavaFX.

\section{O Contrato em Protocol Buffers (\texttt{laboratorio.proto})}

O coração da arquitetura distribuída reside no arquivo \texttt{laboratorio.proto}. Em sistemas, a IDL desacopla o projeto da linguagem de programação, estabelecendo tipos de dados, numeração de campos e assinaturas de métodos RPC de forma determinística.

\subsection{Especificação do Contrato}

A listagem a seguir apresenta a íntegra do contrato implementado no arquivo \texttt{src/main/proto/}\allowbreak\texttt{laboratorio.proto}:

\begin{lstlisting}[language=protobuf, caption={Contrato de Interface (\texttt{laboratorio.proto})}]
syntax = "proto3";

// Pacote logico das mensagens e do servico
package laboratorio;

// Opcoes de geracao para Java (classes geradas pelo compilador protoc)
option java_package = "javafx.laboratorio.grpc";
option java_multiple_files = true;

// Mensagem de entrada: somente o ID do laboratorio
message ConsultarPorIdRequest {
  int32 id = 1;
}

// Mensagem de saida: dados do laboratorio
message ConsultarPorIdResponse {
  string nome = 1;
  string departamento = 2;
  int32 capacidade = 3;
}

// Servico exposto pelo servidor Python
service LaboratorioService {
  // RPC unario: recebe o ID e retorna os dados do laboratorio
  rpc ConsultarPorId (ConsultarPorIdRequest) returns (ConsultarPorIdResponse);
}
\end{lstlisting}

\subsection{Análise Estrutural e Semântica do Contrato}

A especificação do contrato incorpora preceitos fundamentais da especificação \texttt{proto3}:

\begin{itemize}
    \item \textbf{Declaração de Sintaxe e Pacote}: A diretiva \texttt{syntax = "proto3"} estabelece o padrão de terceira geração dos Protocol Buffers. O \texttt{package laboratorio} define o namespace lógico, evitando colisão de nomes.
    \item \textbf{Diretivas de Compilação para Java}: As diretivas de compilação (\texttt{java\_package = "javafx.}\allowbreak\texttt{laboratorio.grpc"} e \texttt{java\_multiple\_files = true}) instruem o compilador a gerar as classes Java diretamente no pacote modular do projeto, gerando arquivos separados para cada mensagem e para a classe do serviço gRPC, mantendo o código-fonte legível e organizado.
    \item \textbf{Mensagens e Numeração de Tags}: Em Protocol Buffers, os campos não são identificados pelo nome textual durante a transmissão de rede, mas sim por números inteiros conhecidos como \textit{field tags} (ex: \texttt{id = 1}, \texttt{nome = 1}, \texttt{departamento = 2}). No formato de codificação binária (\textit{wire format}), a tag e o tipo do campo são combinados em um único byte de cabeçalho, permitindo altíssima compressão de dados e total suporte à retrocompatibilidade.
    \item \textbf{Mensagem de Requisição (\texttt{ConsultarPorIdRequest})}: Contém o identificador do laboratório desejado representado por um inteiro de 32 bits (\texttt{int32 id = 1}).
    \item \textbf{Mensagem de Resposta (\texttt{ConsultarPorIdResponse})}: Agrupa as informações essenciais de retorno: o nome do laboratório (\texttt{string nome = 1}), a área/departamento de atuação (\texttt{string departamento = 2}) e a sua capacidade estimada (\texttt{int32 capacidade = 3}).
    \item \textbf{Serviço RPC (\texttt{LaboratorioService})}: Define a operação unária \texttt{ConsultarPorId}. No modelo unário (\textit{Unary RPC}), o cliente envia uma única requisição ao servidor e bloqueia/aguarda até receber uma única resposta, estabelecendo uma semântica de chamada de procedimento tradicional sobre um stream HTTP/2.
\end{itemize}

\subsection{Processo de Geração de Código (\textit{Stubs})}

A partir do arquivo \texttt{.proto}, o compilador de Protocol Buffers (\texttt{protoc}) é utilizado para gerar os stubs em ambas as pontas da arquitetura:

\begin{enumerate}
    \item \textbf{Ambiente Python}: O comando \texttt{python -m grpc\_tools.protoc} processa o arquivo e produz dois módulos:
    \begin{itemize}
        \item \texttt{laboratorio\_pb2.py}: contém a representação das classes de dados serializáveis (\texttt{ConsultarPorIdRequest} e \texttt{ConsultarPorIdResponse});
        \item \texttt{laboratorio\_pb2\_grpc.py}: fornece a classe base abstrata do serviço (\texttt{LaboratorioServiceServicer}) e a função de registro (\texttt{add\_Laboratorio}\allowbreak\texttt{ServiceServicer}\allowbreak\texttt{\_to\_server}).
    \end{itemize}
    \item \textbf{Ambiente Java}: O compilador gera as classes tipadas com o padrão \textit{Builder} para montagem das mensagens imutáveis, além do stub bloqueante síncrono \texttt{LaboratorioService}\allowbreak\texttt{BlockingStub} (fornecido em \texttt{LaboratorioServiceGrpc}) consumido pelo controlador.
\end{enumerate}

\section{Implementação do Servidor gRPC em Python}

O servidor foi concebido em Python pela sua concisão e facilidade em instanciar serviços com a biblioteca \texttt{grpcio}. O papel do servidor é implementar a interface contratual gerada e responder às requisições do cliente através de RPCs.

\subsection{Código do Servidor (\texttt{server.py})}

A implementação completa do servidor gRPC encontra-se detalhada a seguir:

\begin{lstlisting}[language=python, caption={Servidor gRPC em Python (\texttt{server.py})}]
import logging
import os
from concurrent import futures

import grpc
import laboratorio_pb2
import laboratorio_pb2_grpc
import psycopg2

def get_db_connection():
    env_pass = os.getenv("DB_PASSWORD")
    candidate_passwords = [env_pass, "postgres", "admin"] if env_pass else ["postgres", "admin"]
    for pwd in candidate_passwords:
        try:
            dsn = f"host=127.0.0.1 port=5432 dbname=laboratorio user=postgres password={pwd}"
            return psycopg2.connect(dsn)
        except psycopg2.OperationalError:
            continue
    raise psycopg2.OperationalError("Nao foi possivel autenticar no PostgreSQL com as senhas padrao.")

GRPC_PORT = 50051
logger = logging.getLogger("laboratorio-server")

class LaboratorioServiceServicer(laboratorio_pb2_grpc.LaboratorioServiceServicer):
    def ConsultarPorId(self, request, context):
        try:
            conn = get_db_connection()
            try:
                cur = conn.cursor()
                cur.execute(
                    "SELECT nome, area FROM laboratorio WHERE id = %s",
                    (request.id,),
                )
                row = cur.fetchone()
                cur.close()
            finally:
                conn.close()

            if row is None:
                context.set_code(grpc.StatusCode.NOT_FOUND)
                context.set_details(f"Laboratorio com id {request.id} nao encontrado.")
                return laboratorio_pb2.ConsultarPorIdResponse()

            # Mapeia a resposta para os campos definidos no .proto
            return laboratorio_pb2.ConsultarPorIdResponse(
                nome=row[0],
                departamento=row[1], # Mapeia 'area' para departamento
                capacidade=0
            )

        except psycopg2.Error as exc:
            logger.exception("Erro ao consultar o PostgreSQL")
            context.set_code(grpc.StatusCode.INTERNAL)
            context.set_details(f"Falha ao consultar o banco de dados: {exc}")
            return laboratorio_pb2.ConsultarPorIdResponse()

def serve():
    logging.basicConfig(level=logging.INFO)
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
    
    laboratorio_pb2_grpc.add_LaboratorioServiceServicer_to_server(
        LaboratorioServiceServicer(), server
    )
    
    server.add_insecure_port(f"[::]:{GRPC_PORT}")
    server.start()
    print(f"Servidor gRPC pronto em [::]:{GRPC_PORT}")
    server.wait_for_termination()

if __name__ == "__main__":
    serve()
\end{lstlisting}

\subsection{Detalhamento da Lógica do Servidor}

\begin{itemize}
    \item \textbf{Herança do Servicer}: A classe \texttt{LaboratorioServiceServicer} herda diretamente da classe abstrata \texttt{laboratorio\_pb2\_grpc.LaboratorioServiceServicer}. Ela sobrescreve exatamente o método RPC \texttt{ConsultarPorId(self, request, context)}.
    \item \textbf{Processamento da Requisição}: O identificador buscado é extraído diretamente do objeto Protobuf através de \texttt{request.id}. Em seguida, os dados correspondentes são recuperados.
    \item \textbf{Construção da Mensagem Protobuf}: Ao localizar o registro, o servidor instancia e retorna a mensagem tipada \texttt{ConsultarPorIdResponse} com os campos \texttt{nome}, \texttt{departamento} e \texttt{capacidade}, respeitando estritamente o contrato.
    \item \textbf{Tratamento de Códigos de Status gRPC}: Quando um laboratório com o ID especificado não é encontrado, o servidor faz uso do objeto \texttt{context} para registrar o código de status canônico \texttt{grpc.StatusCode.NOT\_FOUND} acompanhado de uma mensagem de detalhe. Caso ocorra uma falha inesperada ou erro de infraestrutura, é propagado o status \texttt{grpc.StatusCode.INTERNAL}. Isso garante que o cliente gRPC receba uma exceção estruturada com código semântico padronizado, ao invés de mensagens genéricas.
    \item \textbf{Inicialização e Concorrência}: A função \texttt{serve()} instancia o servidor gRPC associando-o a um \texttt{ThreadPoolExecutor} com até 10 trabalhadores simultâneos, abrindo a porta TCP \texttt{50051} para conexões não criptografadas (\textit{insecure port}) e aguardando requisições em modo de escuta.
\end{itemize}

\section{Implementação do Cliente gRPC no JavaFX}

No lado cliente, o desafio central consistiu em integrar a chamada de rede remota com a biblioteca gráfica JavaFX, preservando a responsividade da interface e gerenciando falhas de comunicação sem bloquear o usuário.

\subsection{Código do Controlador (\texttt{buscarLaboratorioGrpc})}

A integração do gRPC com a interface JavaFX está implementada no controlador \texttt{FXMLAnchorPane}\allowbreak\texttt{CadastrosLaboratorios}\allowbreak\texttt{Controller}, no método acionado pelo botão de busca:

\begin{lstlisting}[language=java, caption={Invoca\c{c}\~ao gRPC no Controlador JavaFX}]
// Metodo acionado pelo botao "Buscar gRPC"
@FXML
public void buscarLaboratorioGrpc() {
    // 1) Leitura e validacao da entrada do usuario
    String texto = tfId.getText();
    if (texto == null || texto.isBlank()) {
        exibirAlertaErro("Consulta gRPC", "Informe o ID do laboratorio.");
        return;
    }

    int id;
    try {
        id = Integer.parseInt(texto.trim());
    } catch (NumberFormatException e) {
        exibirAlertaErro("Consulta gRPC", "ID invalido: digite um numero inteiro.");
        return;
    }

    // 2) Desabilita o botao para prevenir cliques concorrentes/duplicados
    btnBuscar.setDisable(true);

    // 3) Executa a chamada gRPC bloqueante em uma thread secundaria (Worker)
    Thread worker = new Thread(() -> {
        ManagedChannel channel = ManagedChannelBuilder
                .forAddress(GRPC_HOST, GRPC_PORT)
                .usePlaintext()
                .build();

        try {
            // Criacao do stub bloqueante a partir do canal
            LaboratorioServiceGrpc.LaboratorioServiceBlockingStub stub =
                    LaboratorioServiceGrpc.newBlockingStub(channel);

            // Criacao da mensagem de requisicao via padrao Builder
            ConsultarPorIdRequest request = ConsultarPorIdRequest.newBuilder()
                    .setId(id)
                    .build();

            // Chamada remota unaria com limite de tempo maximo (deadline)
            ConsultarPorIdResponse response = stub
                    .withDeadlineAfter(5, TimeUnit.SECONDS)
                    .consultarPorId(request);

            final String nome = response.getNome();
            final String departamento = response.getDepartamento();
            final int capacidade = response.getCapacidade();

            // 4) Atualiza os componentes visuais na thread principal da interface
            Platform.runLater(() -> {
                lblNome.setText(nome);
                lblDepartamento.setText(departamento);
                lblCapacidade.setText(String.valueOf(capacidade));
            });

        } catch (StatusRuntimeException e) {
            Status status = e.getStatus();
            if (status.getCode() == Status.Code.NOT_FOUND) {
                // Caso especifico: registro nao localizado no servidor
                Platform.runLater(() -> {
                    lblNome.setText("Nao encontrado");
                    lblDepartamento.setText("-");
                    lblCapacidade.setText("-");
                });
            } else {
                // Outro erro retornado pelo gRPC (ex: INTERNAL)
                Platform.runLater(() -> exibirAlertaErro(
                        "Erro gRPC", status.getDescription()));
            }
        } catch (Exception e) {
            // Falhas de conexao, queda de servidor ou timeout de rede
            Platform.runLater(() -> exibirAlertaErro(
                    "Falha gRPC", "Nao foi possivel comunicar com o servidor gRPC: " 
                    + e.getMessage()));
        } finally {
            // Fechamento seguro do canal de comunicacao
            channel.shutdownNow();

            // Reabilita o botao de busca na interface
            Platform.runLater(() -> btnBuscar.setDisable(false));
        }
    }, "grpc-lab-search");

    worker.setDaemon(true); // Permite encerramento limpo da JVM
    worker.start();
}
\end{lstlisting}

\subsection{Aspectos de Engenharia e Concorrência na UI}

A integração no cliente JavaFX emprega padrões cruciais para sistemas cliente-servidor:

\begin{enumerate}
    \item \textbf{Não bloqueio da JavaFX Application Thread}: Operações de rede sobre sockets possuem tempo de resposta não determinístico. Se a chamada RPC fosse efetuada diretamente na thread principal do JavaFX, toda a interface gráfica congelaria até a conclusão ou timeout da requisição. Para sanar isso, a chamada bloqueante é encapsulada em uma thread separada (\texttt{Thread worker}). A propriedade \texttt{worker.setDaemon(true)} garante que o encerramento da aplicação não fique preso caso uma requisição ainda esteja em trânsito.
    \item \textbf{Sincronização de Estado com \texttt{Platform.runLater}}: O framework JavaFX impõe que qualquer modificação no grafo de cena (\textit{Scene Graph}) e componentes visuais deve ocorrer estritamente na thread de renderização da UI. Por esse motivo, as atualizações dos rótulos (\texttt{lblNome}, \texttt{lblDepartamento}, \texttt{lblCapacidade}) e janelas de alerta são despachadas por meio do método \texttt{Platform.runLater(\dots)}.
    \item \textbf{Prevenção de Requisições Concorrentes Repetidas}: Ao disparar o evento de busca, o botão é imediatamente bloqueado com \texttt{btnBuscar.}\allowbreak\texttt{setDisable(true)}. O bloco \texttt{finally} garante a sua reativação mesmo em cenários de falha, evitando que cliques múltiplos sobrecarreguem o canal de comunicação com requisições redundantes.
    \item \textbf{Definição de Deadline/Timeout}: Chamadas remotas sem controle de tempo podem ficar suspensas indefinidamente caso ocorram partições de rede silenciosas. Através de \texttt{stub.withDeadlineAfter(5, TimeUnit.SECONDS)}, define-se um prazo de 5 segundos para a conclusão do procedimento, disparando uma exceção de timeout caso o limite seja ultrapassado.
    \item \textbf{Tratamento Diferenciado de Códigos de Status}: Ao interceptar a exceção nativa do gRPC (\texttt{StatusRuntimeException}), o código verifica se o status retornado é \texttt{Status.Code.}\allowbreak\texttt{NOT\_FOUND}. Se for o caso, a interface exibe a mensagem amigável \texttt{"Não encontrado"} diretamente nos campos, sem abrir caixas de erro intrusivas. Outros códigos (como \texttt{INTERNAL} ou quedas de conexão) exibem caixas de diálogo informativas detalhadas.
    \item \textbf{Ciclo de Vida do Canal (\texttt{ManagedChannel})}: O canal de comunicação é construído pelo \texttt{ManagedChannelBuilder} em modo de texto puro (\textit{plaintext}) e finalizado pontualmente com \texttt{channel.shutdownNow()} dentro do bloco \texttt{finally}, liberando recursos de sockets e threads do Netty alocadas para o transporte TCP.
\end{enumerate}

\section{Considerações Finais}

A implementação do projeto comprovou na prática as vantagens da utilização do protocolo gRPC e de Protocol Buffers na interoperabilidade entre ecossistemas formados por Python e Java:

\begin{enumerate}
    \item \textbf{Contrato Estrito como Única Fonte da Verdade}: O arquivo \texttt{laboratorio.proto} eliminou ambiguidades de integração. Tanto o servidor Python quanto o cliente Java compartilham os mesmos nomes de mensagens, assinaturas de procedimentos e tipos de dados, garantindo consistência sem a necessidade de documentações manuais suscetíveis a desatualização.
    \item \textbf{Eficiência e Compactação Binária}: Ao substituir formatos baseados em texto (como JSON ou XML) pela codificação binária dos Protocol Buffers, as mensagens trafegam de forma extremamente compacta, reduzindo a sobrecarga na rede e o tempo de serialização/desserialização nas extremidades.
    \item \textbf{Tipagem Forte em Tempo de Compilação}: No Java, a geração de classes via \texttt{protoc} garante que erros de digitação ou divergências de tipos de campos sejam identificados em tempo de compilação, e não em tempo de execução (\textit{runtime}).
    \item \textbf{Tratamento Semântico de Falhas}: A presença de códigos de status canônicos (como \texttt{NOT\_FOUND} e \texttt{INTERNAL}) possibilita que o servidor Python sinalize cenários de negócio ou falhas internas com clareza, permitindo ao cliente JavaFX reagir de maneira granular e elegante na interface gráfica.
\end{enumerate}

Em suma, a solução desenvolvida exemplifica com sucesso os princípios basilares da computação distribuída moderna: desacoplamento de linguagens, tipagem forte, alta performance na camada de transporte e responsividade assíncrona na camada de apresentação.
